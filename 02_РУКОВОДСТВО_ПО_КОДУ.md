# LUBRICA 1.0.33.66 — полное руководство по коду и модулям

## 1. Назначение и архитектурный принцип

LUBRICA — полностью локальное браузерное приложение для построения и эксплуатации программы смазки. Production-архитектура намеренно проста: пользователь распаковывает папку и открывает `index.html` в Microsoft Edge через `file://`. Сервер, VM, backend и сетевой API не требуются.

Код организован как набор обычных `<script>`-модулей. Модули регистрируют API в `window` под именами `Lubrica*`. Порядок подключения в `index.html` является частью архитектурного контракта: ядро загружается раньше доменных модулей, движки — раньше UI, `js/app.js` — после всех основных модулей.

## 2. Главный доменный инвариант

**Мероприятие смазки создаётся только в карточке физической точки.** Оно хранится в `db.tasks`. Маршрут, План смазочных работ, выполнение, ФРВ, аналитика, Контроль и Excel не создают параллельные мероприятия — они только ссылаются на существующий `taskId` и фиксируют состояние/факт.

Одна физическая точка `lubricationPoint` может иметь несколько мероприятий `task` с разной операцией и периодичностью. Поэтому в финальном Excel одна строка «Карты смазки» соответствует одному мероприятию, а не одной физической точке.

## 3. Модель данных

Каноническая схема создаётся в `core/database-schema.js`, `schemaVersion = 2.0`. Верхний уровень рабочей БД:

- `project` — проект/база;
- `plants` — завод;
- `lines` — линии;
- `areas` — участки;
- `equipment` — оборудование и вложенное оборудование;
- `components` — классифицированные/привязанные компоненты;
- `nodes` — узлы оборудования;
- `lubricationPoints` — физические точки смазки;
- `tasks` — мероприятия смазки;
- `materials` — смазочные материалы;
- `tools` — инструменты;
- `routes` — маршруты и их lifecycle/revisions;
- `checklistRuns` — факты выполнения;
- `imports` — история импорта;
- `rules` — инженерные значения по умолчанию;
- `bearingOverrides`, `componentLibraryEntries` — локальные расширения библиотек.

Основная иерархия структуры: **Завод → Линия → Участок → Оборудование → Узел → Физическая точка → Мероприятие**.

## 4. Жизненный цикл загрузки

1. `index.html` создаёт DOM-каркас и подключает CSS/JS.
2. `core/observability.js` начинает контроль загрузки модулей.
3. `core/database-*`, `migration.js`, `storage.js`, `ids.js`, `state.js` поднимают модель данных.
4. Загружаются справочники компонентов/подшипников и калькуляторы.
5. Загружаются структура и импорт.
6. Загружаются маршруты, чек-лист, ФРВ, планирование, аналитика и Контроль.
7. Загружаются UI-модули, экспорт, материалы и редакторы.
8. `js/app.js` завершает инициализацию и связывает пользовательские события.

Если при сопровождении меняется порядок `<script>` в `index.html`, обязательно запускать `test/preflight.py` и полный `test/run_all.sh`.

## 5. Ядро `core/`

### `database-schema.js`
Определяет пустую БД, базовые clean/safeKey/normalization helpers и версию приложения. Это первичный контракт структуры данных.

### `database-normalizer.js`
Используется после открытия/миграции, чтобы отсутствующие массивы и поля не ломали код. Любое новое поле БД должно иметь безопасное значение по умолчанию здесь или в schema.

### `database-migrations.js` и `migration.js`
Первый файл содержит миграционные преобразования v2; второй поддерживает старую v1-модель, где данные исторически могли быть представлены через `points`. При изменении schema нельзя просто переименовывать поля: нужна миграция и тест старой БД.

### `database-safety.js`
Барьер перед активацией внешнего JSON. Проверяет читаемость, известный формат, обязательные коллекции, дубли ID и связи. Синтаксически/структурно опасная база не должна заменять текущую сессию.

### `storage.js`
Recovery в localStorage. Recovery — аварийная копия, не замена пользовательскому backup. Код должен уметь отвергнуть повреждённую recovery-копию и использовать совместимый fallback.

### `state.js`
Единый источник текущей активной БД в runtime. Доменные модули должны получать/сохранять данные через существующий state-контур, а не создавать собственные независимые базы.

### `database-session-ui.js`
Файловые операции. Для Edge может использовать File System Access API при наличии; обязательно сохраняется fallback на обычную загрузку файла. Это критично для `file://`.

### `observability.js` / `diagnostics.js`
Системная диагностика. После удаления старого Checks UI проверяется `Control UI / renderProgramQA`. Диагностика не должна ссылаться на исторически удалённые модули.

## 6. Структура `structure/`

`context.js` хранит текущий `selected`, раскрытые ветви, helpers и правила дочерних сущностей. `tree-ui.js` строит левое дерево. `detail-ui.js` строит правую динамическую карточку. `entity-dialogs.js` редактирует сущности. `point-wizard.js` отвечает за физическую точку. `structure.js` — оркестратор раздела.

Критическая связка UI: клик по `.structure-row` → обновить `C.selected` → перерисовать дерево → вызвать `LubricaStructureDetail.render(d)`. В версии 1.0.1 именно здесь исправлена регрессия статичной правой панели.

## 7. Импорт `import/`

`import-engine.js` читает XLSX через локальный JSZip-контур, создаёт/обновляет структуру и использует устойчивые внешние коды для повторного импорта. Повторный импорт тех же объектов должен обновлять существующие записи, а не плодить дубли.

После импорта `component-classifier.js` определяет типы компонентов, `candidates.js` показывает неоднозначные кандидаты, `candidate-finalizer.js` переносит подтверждённые результаты в рабочую модель, `import-results.js` показывает статистику.

## 8. Компоненты и подшипники

`components/` даёт общий слой библиотек: registry, category schemas, matcher и binding. `bearings/` — специализированная библиотека подшипников и калькулятор. `components/bearing-adapter.js` связывает специализированную библиотеку с общей компонентной моделью.

Правило расширения: новый тип компонента лучше добавлять через registry/schema/adapter, а не через большие условные блоки в UI.

## 9. Расчётный слой `calculations/`

`framework.js` задаёт единый контракт расчётов; `registry.js` регистрирует калькуляторы; `catalog.js` описывает доступные расчётные типы. Специализированные `*-calculator.js` выполняют инженерную математику, а `*-adapter.js` переводят данные между общей моделью и конкретным калькулятором.

Существуют калькуляторы для подшипников, линейных подшипников, редукторов, цепей, муфт, grease points, ШВП, маслосистем, открытых передач, канатов и централизованной смазки.

`engineering-sources.js` и `engineering-sources-ui.js` обеспечивают трассируемость инженерного основания. Расчётное значение не должно автоматически считаться утверждённой инженерной нормой.

## 10. Материалы и инструменты `materials/`

`library-ui.js` ведёт материалы и инструменты. Материал имеет визуальную маркировку цвет + символ. Инструмент не хранит независимую маркировку, а наследует её от привязанного материала. Этикетки печатаются 60×30 мм. Инструмент без материала не должен печатать «материальную» этикетку.

## 11. Мероприятия `lubrication/`

`task-editor.js` редактирует существующее мероприятие точки. Для операций, где материал не требуется (например контроль/осмотр), логика не должна искусственно требовать материал. Для материальных операций должны проверяться материал, инструмент, количество/единица, периодичность и источники.

## 12. Маршруты `routes/`

`route-engine.js` — доменное ядро. Маршрут хранит ссылки на существующие `taskIds`. Создание транзакционное: до финальной команды «Создать маршрут» новый маршрут не должен появляться в БД. Архив — lifecycle state, не удаление.

`route-preparation.js` агрегирует только реально назначенные материал/инструмент. `route-planning.js` формирует предварительный План смазочных работ. Если нет истории, код не должен угадывать первую дату — нужен anchor «Дата первого планового выполнения». `route-planning-ui.js` реализует цепочку: период → предварительный план → проверка → «Зафиксировать план».

`route-plan-fact.js` работает с историческим snapshot/revision, чтобы позднее изменение маршрута не переписывало прошлое. `route-analytics.js` и `management-dashboard.js` строят аналитику на фактах, а не создают новые мероприятия.

## 13. Выполнение и ФРВ `checklist/`

`checklist-engine.js` формирует рабочий лист по зафиксированной ревизии маршрута, хранит результаты по taskId и frozen routeSnapshot. `frv-engine.js` хранит фактические временные категории выполнения. Изменение текущего маршрута не должно менять уже завершённый факт.

## 14. Контроль `qa/`

Несмотря на техническое имя папки `qa`, пользовательский раздел называется **«Контроль»**. `qa-engine.js` read-only: он анализирует БД, но не исправляет её автоматически. Семь областей готовности: структура, точки, материалы, нормы, периодичность, источники, маршруты. Итоговый процент вычисляется по применимым проверкам.

`qa-ui.js` показывает проблемы и через `LubricaWorkspaceNavigation.openTask/openPoint` ведёт пользователя к конкретной записи.

## 15. Финальный Excel `export/`

`final-excel-template.js` содержит base64 принятого XLSX-шаблона. `final-excel.js` распаковывает его через JSZip, заменяет динамические строки и сохраняет стили/merge/ширины. Видимые листы шаблона сохраняются; добавляется расчётно-обосновывающий лист. Для трассируемости taskId хранится в скрытых колонках.

Критическое правило: одна строка листа «Карта смазки» = один `task`. Если у LP-001 четыре мероприятия, в Excel должно быть четыре строки с одной физической точкой и четырьмя taskId.

## 16. Общий UI `ui/`

`view-router.js` — маршрутизация левого меню. `workspace.js` — основная карта и точная навигация к task/point. `checks-settings.js` — настройки, база, backup/recovery, помощь, инженерные defaults. `user-guide.js` — 14-раздельное встроенное руководство. `bulk-edit.js` и `column-dialog.js` — вспомогательные массовые/табличные функции.

## 17. CSS `assets/app.css`

CSS общий и накопительный. При изменении интерфейса опасно добавлять глобальные override для `.btn`, `table`, `dialog`, если проблема относится только к одному модулю. Предпочтительны узкие селекторы контейнера конкретного раздела. После UI-изменений запускать `test_final_ui_baseline_audit.py` и профильные UX-тесты.

## 18. Глобальные API

Основные runtime namespaces: `LubricaCore`, `LubricaStructure`, `LubricaStructureTree`, `LubricaStructureDetail`, `LubricaImport`, `LubricaComponents`, `LubricaCalculations`, `LubricaRouteEngine`, `LubricaRoutePlanning`, `LubricaChecklistEngine`, `LubricaFRV`, `LubricaProgramQA`, `LubricaFinalExcel`, `LubricaWorkspaceNavigation`, `LubricaApp`.

Новый модуль должен либо использовать существующий namespace, либо создать один явно именованный `Lubrica*` API; не рекомендуется оставлять критические функции только локальными, если их вызывает другой файл.

## 19. Как правильно вносить изменения

1. Сделать копию production-папки.
2. Определить владельца функции по папке/модулю.
3. Не менять доменную модель ради визуального исправления.
4. Если меняется schema — добавить нормализацию/миграцию.
5. Если меняется UI-связь между файлами — проверить публичный `Lubrica*` API и порядок scripts.
6. Добавить узкий regression test, воспроизводящий найденный дефект.
7. Запустить `python3 test/preflight.py`.
8. Запустить профильные тесты.
9. Перед выпуском запустить `bash test/run_all.sh`.
10. На целевом ПК открыть `index.html` через Edge `file://` и проверить затронутый пользовательский сценарий.

## 20. Тестирование `test/`

`run_all.sh` — официальный агрегатор. В папке сохранены unit-тесты расчётов, интеграционные тесты БД/импорта/маршрутов, UX-контракты и предрелизные проверки. Это намеренно оставлено в production-архиве как воспроизводимая техническая документация.

Для текущего hotfix добавлены:
- `test_release_1_0_1_structure_detail_interaction.js` — моделирует выбор строки структуры и требует перерисовку правой панели;
- `test_release_1_0_1_structure_detail_static.py` — запрещает возврат к ошибочному локальному `renderDetail(d)` и проверяет исправление карточки завода.

## 21. Диагностика типовых проблем

**Белый/пустой экран:** проверить консоль Edge и порядок script в `index.html`; затем `preflight.py`.

**Панель отображается, но статична:** искать потерянный event handler, неправильный namespace или вызов локальной функции из другого модуля. Сначала проверить выбранный объект (`selected`), затем render-функцию целевой панели.

**JSON не открывается:** проверить `database-safety.js`; не обходить safety прямой установкой State.

**Повторный импорт создаёт дубли:** проверить устойчивость `externalCode` и lookup в `import-engine.js`.

**Маршрут содержит «новое» мероприятие:** это нарушение архитектуры. Маршрут обязан ссылаться на существующий taskId.

**Excel объединяет несколько операций точки в одну строку:** это нарушение контракта экспорта; искать агрегацию по lubricationPointId вместо taskId.

**file:// перестал работать:** искать `fetch`, dynamic import, удалённые URL, Service Worker или обязательную зависимость от File System Access API без fallback.

## 22. Что нельзя удалять при «чистке» архива

Нельзя удалять `index.html`, `manifest.json`, функциональные JS, `assets/app.css`, `assets/guide`, `vendor/jszip.min.js`, встроенный Excel template, справочные данные/источники и тесты, если требуется возможность сопровождения. Исторические отчёты Stage/RC можно удалять: они не участвуют в runtime.

### 1.0.1 — Structure right panel hotfix

В `structure/tree-ui.js` после выбора объекта дерево обязано вызвать публичный `LubricaStructureDetail.render(d)`. В 1.0.0 ошибочный вызов несуществующей локальной `renderDetail(d)` приводил к тому, что правая панель визуально оставалась статичной. Regression-контракт сохраняется в `test_release_1_0_1_structure_detail_interaction.js` и `test_release_1_0_1_structure_detail_static.py`.

Также исправлено поле описания завода: `x.description`.

### 1.0.2 — Branding & Icons

Версия 1.0.2 не меняет доменную логику. Она добавляет фирменное оформление приложения, favicon и Windows-ярлык.

## 24. Branding, favicon и Windows-ярлык

Все фирменные изображения хранятся **только** в `assets/icons/`.

### `lubrica-header.png`

Прямоугольный логотип, предназначенный специально для левого верхнего угла `topbar`. В `index.html` он подключён как:

```html
<div class="brand brand-logo">
  <img src="./assets/icons/lubrica-header.png" alt="LUBRICA">
</div>
```

Размер ограничивается CSS-селекторами `.brand.brand-logo` и `.brand.brand-logo img`. Логотип не должен увеличивать штатную высоту topbar в 64 px и не должен выталкивать блок текущей базы или кнопки вправо.

### `lubrica-app.png`

Полноразмерная квадратная фирменная иконка. Это master PNG для использования внутри документации, презентаций и будущих системных интеграций. Runtime напрямую от неё не зависит.

### `lubrica-shortcut.png`

PNG-исходник иконки рабочего стола. Нужен как удобный master для последующей регенерации `.ico`.

### `lubrica-shortcut.ico`

Windows ICO с несколькими слоями: 16, 24, 32, 48, 64, 128 и 256 px. Используется только ярлыком Windows. При замене этого файла не надо менять код приложения, если имя/путь сохраняются.

### `lubrica-favicon-*.png`

Набор favicon 16/32/48/64/128/180/256 px. В `index.html` явно подключены основные 32, 64, 128 и Apple-touch 180. Иконки локальные, поэтому `file://` не требует сети.

### `Создать ярлык LUBRICA.bat`

Это вспомогательный Windows-скрипт, а не часть JS-runtime. Он:

1. получает корневую папку через `%~dp0`;
2. находит установленный Microsoft Edge;
3. получает путь к рабочему столу через PowerShell;
4. создаёт `LUBRICA.lnk`;
5. задаёт `msedge.exe` как TargetPath;
6. передаёт локальный `index.html` как аргумент;
7. устанавливает `assets/icons/lubrica-shortcut.ico`;
8. задаёт рабочую папку проекта.

Скрипт не копирует базу данных и не модифицирует приложение.

## 25. Как менять фирменные изображения

Если дизайн обновляется:

1. Не менять имена runtime-файлов без необходимости.
2. Новый прямоугольный логотип сохранять как `assets/icons/lubrica-header.png`.
3. Проверять его при Edge 100%, а также при ширине окна около 1200–1450 px.
4. Из квадратного master заново выпускать favicon, а не растягивать маленький 32×32.
5. `.ico` собирать многослойным, иначе Windows будет плохо масштабировать ярлык.
6. После замены выполнить `python3 test/test_release_1_0_2_branding.py`.
7. Затем выполнить `python3 test/preflight.py` и `bash test/run_all.sh`.

## 26. Чистая production-поставка

В корне 1.0.2 намеренно оставлены только функциональные файлы и два постоянных документа. Исторические `STAGE*`, `RC1*`, `RC2*`, `APPROVAL*`, старые audit/test-output и прошлые SHA256-отчёты удалены.

Это не означает удаление тестов. Папка `test/` остаётся частью сопровождаемой поставки, потому что она позволяет воспроизвести архитектурные и regression-контракты.

Полный актуальный список **каждого** файла находится в `01_СОСТАВ_АРХИВА.md`.

## 27. Минимальный checklist разработчика перед новой версией

## 1.0.33.50 — Oscillating / Linkage lifecycle и защита реальной базы

`oscillating/oscillating-linkage-arrangement.js` — расширяемый arrangement-engine для системы качания, КШМ, шатунов, тяг, осей, компенсаторов и связанных ролей. Роль элемента не является точкой смазки: точка появляется только после подтверждения фактического bearing/housed bearing/SNL/bushing/joint/guide или другой обслуживаемой пары.

Повторное сохранение конструктора работает как scoped synchronization. Только артефакты с origin `equipment:<rootId>:osc_*`, которых больше нет в подтверждённом наборе, удаляются из рабочей карты; чужие/ручные точки не затрагиваются. Связанные активные route `taskIds` очищаются от удалённого generated task, исторические revision/checklist snapshots не переписываются.

Classifier не использует правило «единственная система качания в area/line». Автоматическая принадлежность строится по `oscillatingContextRootId`, ancestor hierarchy или однозначному `Линия №N`; при слабом доказательстве элемент остаётся отдельным review-кандидатом.

Для ручного SKF SNL точка хранит нейтральный `bearingHousing={family:'SNL', rawMarking, source:'oscillating_linkage'}`. `lubrication/task-editor.js::bearingHousingContext36()` учитывает этот context и `installedComponent`, поэтому SNL service policy выбирается тем же resolver, что для импортированной конструкции.

Для SKF SNH используется тот же нейтральный `bearingHousing`, но с `family:'SNH'`. Корпус и внутренний подшипник не смешиваются: `sourceRef` точки остаётся внутренним подшипником, а SNH хранится как housing-context. Task Editor показывает SNH как отдельную корпусную опору; расчёт дозы идёт по внутреннему подшипнику, а полный запас смазки корпуса не утверждается автоматически без отдельной подтверждённой SNH-методики.

Защитные правила реальной базы применяются до создания точки. Компоненты с `candidateState=excluded/rejected`, закрепительные втулки H-серии и зажимные устройства TOLLOK TLK 400 не попадают в обслуживаемые ТМЦ. Маркировки закрытых подшипников `2RS`, `2RS1`, `2RSH`, `2Z`, `ZZ`, `DDU`, `VV` блокируют автоматическое рутинное досмазывание как при выборе импортированного ТМЦ, так и при ручном вводе. Если пользователь выбирает корпус SNL/SNH как обычный `bearing`, сохранение требует переключиться на тип корпусной опоры и выбрать фактический внутренний подшипник.

`non_serviceable` и `no_connection` — разные подтверждённые состояния без точки. Legacy `none` мигрируется на `non_serviceable` при открытии/сохранении конструктора. Ручные элементы, созданные самим мастером (`componentType=manual_oscillating_element`, `manualOscillatingKey`), можно удалять повторно; cleanup не затрагивает импортированные компоненты.
