# LUBRICA — стратегия тестирования и приёмки

## 1. Уровни проверки

Каждое существенное изменение проходит несколько уровней:

1. preflight / статическая проверка;
2. узкий тест на конкретный дефект или новую функцию;
3. интеграционные проверки затронутых модулей;
4. полный `test/run_all.sh`;
5. проверка на актуальной производственной JSON-базе, если изменение касается данных, binding, migrations, constructors или расчётов;
6. ручная проверка затронутого сценария в Edge через `file://`.

## 2. Обязательные invariants

Для конструкторов и machine profiles:
- повторное применение не создаёт дублей;
- entity counts не растут без причины;
- origin keys стабильны;
- manual add и import дают одну логику;
- Line/analog parity не нарушена.

Для расчётов:
- новый OEM dataset не оставляет старое auto-approved значение валидным;
- источник и provenance сохраняются;
- результат не применяется к мероприятию без явного lifecycle;
- cross-OEM guards работают;
- после reload/reconcile данные не меняются неожиданно.

Для маршрутов:
- маршрут использует существующие taskId;
- архив/история не переписываются;
- snapshot завершённого выполнения сохраняется.

Для Excel:
- одна строка = одно мероприятие;
- taskId сохраняет трассируемость;
- структура принятого шаблона не ломается.

## 3. Regression

Полный regression — обязательное условие принятой версии.

Для 1.0.33.67 финальный набор checkpoints 1–99 прошёл PASS.

Если техническое ограничение среды прерывает длинный запуск, допустимо продолжить оставшиеся checkpoints отдельными блоками. Сам timeout не считается функциональной ошибкой, если выполненные тесты PASS и оставшиеся проверки затем завершены.

## 4. Acceptance package

Каждая принятая версия должна иметь:
- release note;
- regression acceptance;
- при необходимости отдельный инженерный acceptance;
- обновление `PROJECT_STATE_RU.md`;
- обновление `RELEASE_HISTORY_RU.md`;
- тег Git;
- при необходимости release artifact ZIP + SHA-256.

## 5. Что нельзя считать достаточной проверкой

- только открыть экран;
- только проверить новую кнопку;
- только прогнать unit test;
- только увидеть корректное число без проверки источника;
- проверить импорт, но не manual add;
- проверить первый apply, но не повторный;
- проверить runtime, но не persisted JSON после reload.
