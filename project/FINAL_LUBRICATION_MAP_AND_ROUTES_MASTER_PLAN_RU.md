**Редакция:** 2026-11-09, исправлено по решению пользователя.
**Статус:** утверждён порядок стадий разработки; production JSON не изменялась, ни одна будущая стадия не считается закрытой автоматически.
**Источник:** производственная JSON от 2026-11-05; `main` 1.0.33.71 RC; PR #20, #21, #22; `project/PLANT_POINT_COMPLETION_PLAN_RU.md`, аудит реальных 1188 единиц оборудования.

## Ключевое решение о порядке работ — НЕ МЕНЯТЬ

**СНАЧАЛА завершить все необходимые конструкторы для всего реально смазываемого оборудования и физических точек обеих линий → ЗАТЕМ закончить карту: точки, мероприятия, материалы, нормы, интервалы, OEM, утверждения → ТОЛЬКО ПОСЛЕ этого переходить к производственным маршрутам, планам, фактам и окончательному Excel.**

- **Никаких параллельных маршрутных пилотов, создания production routes или переноса части неготовой карты в маршруты до завершения и приёмки всех конструкторов.** Предыдущая идея параллельного «route pilot» отменена решением пользователя.
- Рабочие программные модули маршрутов, чек-листов, план/факт и Excel сохраняем; не удалять и не переписывать. Их существование не означает, что настало время создавать маршруты.
- «Закрыть все конструкторы» означает **полное покрытие реальных физических типов смазываемых узлов**: специализированный конструктор для существенного семейства или доказанно эквивалентный расширяемый универсальный, с поддержкой каждой реальной конфигурации и ручного добавления. Не делать отдельный движок для каждого артикула, подшипника или модели, если семейный конструктор полностью покрывает физику.
- `group / structure / no-lube / not-applicable` фиксировать явно и с источником; группа оборудования не превращается в отдельную смазочную точку. **Ноль необъяснённых пропусков по применимому оборудованию** — условие закрытия конструкторного этапа.
- Если OEM/чертёж/осмотр не подтверждает физическую опору, смазочную маслёнку или полость, оставить `REVIEW/SOURCE_REQUIRED` и точную задачу инженерной проверки; **не выдумывать** опору ради формального закрытия. Такой блокер означает, что конструктор ещё не принят для данной физической конфигурации.

## Стадия К0 — полная матрица оборудования и физических семейств (обязательный вход в конструкторы)

Проход по реестру из 1188 `equipment` и 5659 `components`, двум линиям и структуре родителей/детей; центрифуги и связанные с ними подсистемы (как и системы охлаждения) помечать `OUT_OF_SCOPE` без предметного инженерного разбора, не удалять и не переклассифицировать их исходные данные.

Для **каждой** записи определить: `PHYSICAL_MACHINE`, `PARENT_COMPOSITE`, `STRUCTURE_ONLY`, `ANCILLARY_CONTEXT`, `NON_LUBRICATED`, `NOT_APPLICABLE`, `REVIEW`. Для каждой физической машины перечислить:
- семейство и точный подтип, фактическую конструкцию и иерархию;
- исходные ТМЦ и source refs, внешние коды, подтверждённые обслуживаемые подузлы и количество *реальных* мест;
- какие обслуживаемые точки уже существуют, какие предложены и какие отсутствуют; не перепутать одну типовую строку подшипника с фактическим количеством опор;
- подходящий существующий конструктор, фактические покрытые и неподдерживаемые возможности, блокеры OEM/полевого подтверждения;
- решение на каждый компонент: `POINT / CONTEXT / NO_LUBRICATION / CLARIFY`; статусы подтверждения и источник;
- наличие аналога на другой линии — только как кандидат для *инженерного сравнения*, не для безусловного дублирования схемы.

**Результат К0:** машиночитаемая матрица `equipment → machine_family → required_arrangement → confirmed_points → unsupported → next_action`, сгруппированная по линии/участку. Все агрегаты из `other` проверять на физическую применимость, не объявлять 812 `other` = 812 новых движков. Приоритет сортировки — реальная обслуживаемость/риск/незакрытые ТМЦ, а не алфавит.

## Стадия К1 — довести существующие конструкторы до полного охвата

Проверить функциональный полный цикл для:
- подшипниковые узлы (SKF/NSK/FAG/NTN-SNR/Timken) и вращающиеся валы/барабаны/ролики, типы подшипников и корпуса, исключение заводских sealed;
- Fan Bearing Arrangement: REITZ, Ferrari совмещённые узлы/SNL, Ventapp+Tröster, SNR ZLG (фактические 2 маслёнки), без SNR DLG и виртуальных опор; 24 неизвестных шаблона разобрать по физике;
- приводы, электродвигатели, редукторы и составные масляные полости (K37, R77, KF37R17, S37, Bonfiglioli, Rossi, Tandler и установленные аналоги), M1–M6 только после фактического выбора, не выводить из токена моторной маркировки;
- цепи, скользящие/линейные подшипники, муфты, шарниры, открытые зубчатые передачи, винтовые подъёмники, маслосистемы, где есть реальные физические обслуживаемые места;
- PP-53736 как принятую программную базу со 102 фактическими подшипниковыми позициями/8 цепями/4 винтами/раздельными редукторными полостями — не ломать этот acceptance.

**Результат К1:** по каждому поддержанному семейству доказана полная физическая topology + component ID + location + available maintenance action; отсутствие OEM данных оставляет `review` вместо скрытой утверждённой нормы.

**Результат К2:** по каждой реально смазываемой машине имеется работоспособный соответствующий конструктор (или полностью подходящий универсальный), без пропусков/фиктивных подшипников/дублирования родителя и детей. Модели с недоказанной физикой остаются явным **инженерным блокером** приёмки, а не считаться готовыми.

## Стадия К3 — единая интеграционная приёмка ВСЕХ конструкторов (жёсткий стоп перед маршрутами)

Испытать каждый тип машин и комбинаций на **обеих линиях**, включая `manual add`, повторный импорт, выбранный аналог, изменение физической схемы, preview → apply → save → reload, component binding, источник/OEM, перенос материальных настроек только при физическом соответствии.

**Критерии закрытия К0–К3:**
1. Все **входящие в объём** equipment получили осмысленную инженерную квалификацию с источником или явно разрешённую причину неприменимости; позиции центрифуг/их смазочных подсистем и систем охлаждения отдельно посчитаны как `OUT_OF_SCOPE` без выводов об обслуживаемости. Parent/group/ancillary не считаются самостоятельными смазываемыми агрегатами.
2. **100% фактически смазываемых семействах оборудования и физических местах** есть поддержанный путь через конструктор; все явно выявленные неподдержанные физические конфигурации исправлены.
3. Не осталось необработанных/неразобранных `POINT/CONTEXT/NO_LUBE/CLARIFY` по компонентам, которые могут влиять на полноту смазки; недостающий OEM/фото/полевое место требует решения, а не замены предположением.
4. 0 виртуальных опор, 0 новых ложных точек, 0 дублей при repeated apply, 0 потерь approved/route/fact и зависимостей; корректная композиция сложных машин.
5. Для каждого типа конструкторов: targeted tests + full regression + проверка копии реальной JSON + ручная приёмка в Edge `file://` + SHA-256 ZIP. PR #20, #21, #22 объединять только после интеграционного аудита, не считать draft production.
6. **Маршруты не создавать до завершения К3.** При наличии полевых блокеров составить точный реестр, запросить источники/подтверждение и продолжить завершение; не «обходить» через маршрутный пилот.

**Итог этапа конструкторов:** подписываемый реестр оборудования, применимых физически обслуживаемых позиций, точек, исключений, OEM-блокеров и соответствующих конструкторов. Только после закрытия фактических блокеров — «Конструкторы завершены».

## Стадия М1 — конечная карта смазки: точки и мероприятия

**После К3** проверить 501 существующую точку и 517 мероприятий на исходном срезе; расширить по фактически выявленным смазываемым местам, не предрешая итоговое число. У каждого `pointId`: физическое место/способ подачи, оборудование/узел, binding source, service policy. У каждого `taskId`: операция, материал (если нужен), доза/единицы/условия, периодичность, OEM/обоснование, явное `calculate → apply → approve`.

- Проверить статусы 45 approved / 468 review / 4 disabled и пропуски материала/норм/интервалов по **применимости**;
- OEM-достоверность SKF sealed 2CS, материальный паспорт Mobilgear XP 220 (`MAT-0003`), двухполостные редукторы, конвейеры, вентиляторы; исправления через preview/recovery;
- M1–M6 выбирает пользователь для SEW; `5000/500 h` = 5000 ч рабочий интервал, 500 ч first service; никаких скрытых автозамен;
- отчёт готовности с независимыми шагами QA и перечнем требующих подтверждения; нельзя выдать `review` как готовый.

**Закрытие М1:** получена полная конечная карта всех подтверждённых фактических смазываемых точек. Нет «готовых» задач с необоснованным материальным/физическим/OEM/сроковым пробелом. Неподтверждённые факты не подменяются фиктивными approvals.

## Стадия R — маршруты ТОЛЬКО ПОСЛЕ закрытия К3 и М1

1. Проверить и довести `routeEligible(task)` как единый gate на основе `qa/task-readiness`; текущий `route-engine.js:eligibleGroups` использует только `approvalStatus`, а `validateRoute` не закрывает всю инженерию. Нельзя группировать пропуск интервала как активный маршрут «Без периодичности».
2. После полной готовности карты формировать маршруты обеих линий по реальному физическому обходу, участку, периодичности/моточасам, исполнителям, инструментам и материалам; сохранить ревизии.
3. Каждое `approved + QA-ready` **плановое** мероприятие — ровно в одном штатном маршруте, если нет явно документированного исключения; ремонтные/event-based/condition-based — отдельная политика без подмены календарём.
4. Плановая дата первого исполнения и прогноз моточасов только при явном выборе эксплуатационных параметров. Цепочка `task → route → routePlanItem → checklistRun → fact → plan/fact → Excel`, сохранение после reload, snapshot выполненных задач.
5. `export/final-excel.js:taskRows` сейчас экспортирует все, кроме disabled, включая review: создать режим **«Утверждённая карта» = approved + QA-ready**, отдельно **«Инженерный реестр»** и документы маршрутов/планирования/расхода; `taskId` трассируем по всем этапам.

**Закрытие R:** 100% пригодных подтверждённых плановых мероприятий распределены по действующим маршрутам без повторов и пропусков, ни одного approved-but-unready в маршрутах, проверен полный план/факт, Excel и резервное восстановление.
