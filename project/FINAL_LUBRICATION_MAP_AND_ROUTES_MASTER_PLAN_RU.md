# LUBRICA — мастер-план завершения производственной карты и маршрутов смазки

**Дата аудита/плана:** 2026-11-09. **Статус:** проект плана на согласование, не утверждённая production-поставка.
**Источник фактов:** предоставленная пользователем база `Филиал_завода__Техно__г._Юрга(20261105-040121).json`; `main` 1.0.33.71 RC; `project/PLANT_POINT_COMPLETION_PLAN_RU.md`; проверка исходников QA/route/export; PR #20, #21, #22.
**Приоритет:** конечная достоверная карта + маршруты, не отдельные экраны/каталоги. Разрабатывать функциональными пакетами с общей приёмкой, без микро-PR.

## 0. Что считаем готовым продуктом

1. **Полнота охвата:** для каждого оборудования предприятия установлено, есть ли собственные обслуживаемые смазочные места; если нет — доказанная причина `NOT_APPLICABLE / CONTEXT / NOT_LUBRICATED`. Неразобранное оборудование находится в отдельном реестре исключений и не маскируется числом «готовых» точек.
2. **Карта:** каждой подтверждённой физической точке назначены уникальный ID, оборудование, узел, физическое расположение, способ доступа/подачи, исходный ТМЦ/источник, категория и инженерное решение. Одна точка может содержать несколько `taskId`.
3. **Мероприятия:** для каждого актуального действия указаны операция, статус, материал (если требуется), норма и единицы, периодичность или обоснованный режим «по состоянию», OEM/расчёт/основание, инструмент (по необходимости). `approve` — отдельный явный шаг после `calculate → apply`. Отсутствующие подтверждения — `review`, не выдуманные значения.
4. **Маршруты:** каждое пригодное и утверждённое плановое мероприятие учтено в рабочем маршруте ровно один раз, если только документированная схема не предусматривает повторное включение; маршруты сгруппированы по линии, участку, сроку/наработке и реальному физическому обходу. Участки и дочерние машины не создают дубликаты.
5. **План/факт:** действующие маршруты создают плановые задания; поддерживают дату первого исполнения, отдельную наработку в моточасах и отклонения; выполненный маршрут даёт сохранённый чек-лист, snapshot/revision и факт расхода.
6. **Конечный пакет:** валидная production JSON + резервная копия + Excel «Карта смазки» + реестр маршрутов/план + перечень материальной потребности + отчёт качества, исключений и источников. Неподтверждённые строки не смешиваются с утверждённой картой.

**Не допускается:** виртуальные опоры, точки из монтажных деталей, скрытое OEM-фолбэч-утверждение, удаление старых `approved`/маршрутов/фактов, переписывание пользовательского JSON или автоматическая подстановка календаря вместо моточасов. Охлаждающие системы исключены из предметного аудита по указанию пользователя; их не анализировать.

## 2. Выявленные архитектурные разрывы

- `routes/route-engine.js:eligibleGroups` берёт `approved/ready` task, но не проверяет целиком `qa/task-readiness.js` и не исключает утверждённое задание с критической проблемой. `taskContext` подставляет «Без периодичности» для пустого срока; `validateRoute` контролирует наличие task/point, дубли и принадлежность, но не все инженерные требования.
- `routes/route-preparation.js` проверяет часть обязательных реквизитов, но единый gate для норм/материалов/источника/периодичности при включении и планировании отсутствует. Нужен один согласованный, тестируемый предикат `routeEligible(task)`, не вторая таблица правил.
- `export/final-excel.js:taskRows` включает все task, кроме `disabled`, включая `review`. Для производственного «Финальная карта» нужен **approved + QA-ready** режим; для инженерного аудита — отдельный полный экспорт, явно помеченный как черновой.
- `main` 1.0.33.71 RC и отдельные DRAFT PR #20 (материалы), #21 (gap audit), #22 (Stage 5B constructors); успешный CI не заменяет ручную Edge/JSON приёмку. Не смешивать ветки без интеграционных тестов.

## 3. Пакеты работ — выполнять последовательно, демонстрируя работающий сквозной результат

### Пакет A — единый достоверный baseline и «покрытие карты»

- Снять копию пользовательской JSON, контрольный SHA-256, read-only snapshot численности и связности equipment/component/node/point/task/material/route/fact.
- Отчёт **по каждой линии → участку → оборудованию**: число исходных ТМЦ, существующих точек/мероприятий, связанные кандидаты, изолированные/дублированные записи, отсутствующие источники, подтверждения оператора, `NO_LUBE/CONTEXT/REVIEW`.
- Ключевая метрика: `equipment_review_coverage = confirmed decisions / applicable equipment`, отдельно `point_readiness`, `task_readiness`, `route_coverage`. Не использовать `501/1338` как «полноту».
- Обработать статус каждой из 1188 equipment позиций: `SERVICED / NOT_LUBRICATED / STRUCTURE / NOT_APPLICABLE / NEEDS_REVIEW` с причиной; связанные дочерние машины учитывать отдельно, без удвоения.
- Контроль повторного импорта и восстановление копии базы в Edge `file://`; если исходная JSON обновилась, сравнить версии и не терять изменения.

**Приёмка A:** воспроизводимый реестр пробелов + сортировка по значимости/участку; 0 незаметных потерь/изменений JSON; отчёт показывает «какие оборудования ещё не разобраны» по обеим линиям.

### Пакет B — завершить реальные физические точки

- Сначала согласовать и исправить известные дефекты в 501 точке, затем пройти непривязанные реальные компоненты и механизмы. Предъявлять по каждой машине короткую инженерную карточку: найденные детали → сколько именно мест → обслуживается ли → источник → решение.
- Разбирать батчами семейств, а не скриншот на каждый компонент. Приоритет по текущему машинному аудиту: центрифуги/шпиндели и маслораспыление; конвейеры (226 отдельных машин, 35 групп, 32 подсистемы); распиловка/пилы/каретки; вентиляторы (24 незавершённые fan-arrangement); затем питатели, щёточная очистка, штабеллеры/подъёмные механизмы, LINDNER VEGA 1500, маслостанции. Сортировать внутри по числу кандидатов и критичности. **Системы охлаждения не анализировать.**
- Применить Stage 2 решения: `physical point / context / no lubrication / clarify`. «Не смазывается» не удаляет исходные ТМЦ или исторические работы. Действия `point/context` требуют физической позиции и источника.
- Использовать Stage 5B для ручной/импортной проверки конвейеров и составных родительских машин; Stage 5C/5D отдельным *функциональным пакетом*, только если текущие мастера не могут подтвердить реальную схему.
- Между линиями переносить только доказуемое сопоставление `equipmentId` и физической конфигурации; не копировать ID, факты, утверждения и OEM без оснований.

**Приёмка B:** у каждой применимой машины есть согласованное решение по физическим местам; 0 неподтверждённых виртуальных опор; 0 дублей; все unresolved перечислены в отчёте исключений с ответственным/действием.

### Пакет C — завершить точка → операция → OEM → утверждение

- Для всех существующих и добавленных `taskId` пройти 7 шагов `qa/task-readiness.js`; группировать причины отказов для массовой инженерной проверки без автозаполнения.
- Объединить безопасный material passport fix PR #20 (проверка `MAT-0003`), SKF 2CS conditional relubrication, OEM для подтверждённых подшипников/редукторов/цепей/винтов.
- Для редукторов K37/KF37R17/R77/S37 выбор M1–M6 — явный пользовательский шаг; `5000/500 h` = рабочий интервал 5000 ч + first service 500 ч. Для KF37R17 две независимые масляные полости.

### Пакет D — полноценный двигатель готовности маршрутов и пилот

- Сделать **единый** `routeEligible(task)` на базе существующего QA и применить к авто-созданию, ручному включению, маршрутам, плану и подготовке к исполнению. Не смешивать `approvalStatus` с QA-государством `ready`.
- Блокировать в активной маршрутной очереди orphan/duplicate/необоснованную физику/OEM, неподтверждённый материал и норму для нуждающейся в материале операции, пустой источник/период. «По состоянию»/событию — отдельный режим, не ложный календарный маршрут «Без периодичности».

**Приёмка E:** 100% eligible плановых задач включены в однозначный действующий маршрут; у всех активных периодических маршрутов определена политика дат/наработки; успешно выполнены trial run/факт в копии БД.

## 4. Реализация без затягивания

**Первые два результата готовить параллельно, но строго без ослабления QA:** (i) полный read-only реестр покрытия двух линий из пакета A, (ii) безопасный маршрутный пилот на уже утверждённых, реально готовых мероприятиях из пакета D. При этом пакет B/C закрывает недостающее по оборудованию. Не ждать исправления всех 1338 кандидатов, чтобы проверить маршрутный workflow; и не выдавать маршрутный пилот за полноту карты.

Функциональные PR/поставки, а не микро-PR:
1. **Delivery 1 — Coverage + Route Gate + Pilot:** сквозной отчёт, route eligibility, проверка на двух линиях с ограниченным confirmed scope.
2. **Delivery 2 — Fleet Physical Completion + OEM/Materials:** объединение PR #20/#21/#22 через интеграционную приёмку, реальные точки по приоритетным семействам, исправления материалов/расчётов и решение QA.
3. **Delivery 3 — All Routes + Plan/Fact + Final Excel + Release:** все approved-ready задания, 2 линии, Excel и backup/recovery, конечный production package.

**Что необходимо от предприятия только там, где не выводится из данных:** реальные позиции узлов/маслёнок, заводские паспорта, режим работы/наработка, фактическая текущая смазка/совместимость, M1–M6, способ доступа, маршрут обхода/смены, ответственный инженер за утверждение. Программа не вправе молча заполнять эти пробелы.
