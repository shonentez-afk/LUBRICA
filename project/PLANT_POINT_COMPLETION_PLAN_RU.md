Ручная Edge `file://` приёмка на пользовательской базе ещё необходима. Issues #11–#14 остаются открытыми. Production predecessor: **1.0.33.68**. ## Цель

Довести существующую производственную базу предприятия до максимально полной **физически подтверждённой карты обслуживания**, не создавая виртуальных опор, смазочных мест и мероприятий и не выдавая универсальные расчёты за OEM.

Цепочка: **импортированный компонент → физическая точка → действие → материал → инженерный расчёт/источник → применение → утверждение → план/маршрут → факт → Excel**.

Документация пользователя и 23 скриншота намеренно отложены до завершения функциональных этапов; существующее руководство сохраняется.

## P0 — безопасные инженерные проверки (Issue #11)

1. Расширить существующий read-only `qa/qa-engine.js`, **не** создавать вторую систему контроля.
2. Для SKF sealed spherical roller `BS2-…-2CS/VT143`: не объявлять подшипник «навсегда необслуживаемым», потому что SKF допускает conditional relubrication. При наличии `regrease` требовать OEM life assessment, фактически доступный lubrication channel, совместимость смазки и OEM-методику. Reference OEM: `Gp=0.0015*D*B` [g] только в сценарии, когда релубрикация действительно необходима.
3. Для sealed `full_grease_replacement`: предупредить о необходимости именно OEM service procedure и корректной операции — не приравнивать к обычной вскрытой опоре.
4. Materials validation: плотность (г/см³), физически подозрительные значения, для масел — проверка приблизительной согласованности `ISO VG` и вязкости при 40 °C. Не подставлять выдуманные сведения.
5. Отдельные targeted tests на точной SKF-модели и Mobilgear + read-only invariant.
6. После проверки в коде — предложить транзакционную коррекцию данных MAT-0003 с backup/preview; не редактировать предоставленный production JSON автоматически.

**Важный OEM-поправочный вывод:** каталоги SKF прямо содержат relubrication features для sealed SKF Explorer BS2. Поэтому автоматическое `NO_ROUTINE_RELUBE` для всех 2CS было бы ошибкой. OEM источник: https://www.skf.com/binaries/pub12/Images/0901d196808a4ad1-Spherical-roller-bearings_18406-EN_tcm_12-480491.pdf

**Mobil:** https://www.mobil.eu/en-gb/lubricants/products/products/mobilgear-600-xp-220 — `density @15.6°C=0.89 kg/l`; `viscosity @40°C=220 cSt` как типовые данные, проверить edition TDS перед записью в рабочую БД.

## P1 — очередь реальных кандидатов (Issue #12)

1. Список `components` только с доказательными категориями и `candidateState=candidate/review`, сгруппированный по реальному `equipmentId`.
2. Подсчитать связанность с уже существующими физическими точками, не выдавать связанные компоненты за «ещё не созданные точки».
3. Фильтр линии, приоритет по категории и переход к оборудованию — в существующей вкладке «Контроль», без полного редизайна.
4. Следующая итерация: явные решения `создать физическую точку`, `контекст`, `не смазывается`, `уточнить`; каждое решение сохранять с доказательствами и stable origin key, с preview и undo.
5. В конвейерах валы/ролики — контекст до подтверждения установленного подшипника; звездочка сама по себе не точка.

## P2 — готовность/аналоги (Issue #13)

1. Объяснять причину `review` и выдавать **одно следующее действие** на уровне точки/мероприятия.
2. В простом режиме — результат без сырого OEM; в экспертном — цепочка источников и confidence.
3. «Копировать схему с аналога Л1↔Л2» только после подтверждения совпадающей физической конфигурации, без переноса IDs, серийных данных, факта и approvals.
4. Нет автоматического утверждения при изменении исходных данных; calculation apply и task approval остаются разными операциями.
5. Верифицировать `reload/reconcile`, `manual/import parity`, `repeated apply`, `one task = one Excel row`.

## P3 — производственное завершение (Issue #14)

Сортировать оборудование по числу существенных нерешённых кандидатов и критичности: упаковки/распиловки/камеры/вентиляторы по данным, а не по догадкам. Fan Arrangement Wizard — только реальные bearing arrangements (REITZ, SNL, SNR ZLG, Tröster на Ventapp, Ferrari integrated etc.). Поддерживать расширяемый OEM слой.

## Acceptance gates

- ноль автоматически созданных виртуальных точек;
- ноль потерь пользовательских `approved` данных/маршрутов/истории;
- ни одного молчаливого OEM-fallback как «подтверждённый OEM»;
- issue severity и подсказки воспроизводимы на production JSON;
- переходы из QA открывают реальные equipment/points/tasks;
- targeted tests + full regression + Edge `file://` smoke test;
- ни один JSON-файл пользователя не перезаписывается автоматически;
- для завершённой пользовательской карты проверяется реальная цепочка `approved task → route → plan → run/fact`; пустые массивы маршрутов не заполняются из `review` без подтверждения.

## Текущая итерация (начата)

P0: инженерные QA checks + read-only кандидатная очередь P1 (первый проход) + targeted test + regression; без переписывания калькуляторов и без изменения исходных production-data.


## Stage 2 (engineer decisions) — реализованный контракт

- `qa/engineering-decisions.js`: решения `point/context/not_lubricated/clarify`, причина и источник для физически значимых действий, read-only preview, idempotent commit, guarded undo.
- `qa/qa-ui.js`: разворачивание ТМЦ по оборудованию, постраничный список, модальный предпросмотр, история решений и защищённая отмена.
- `import/candidate-finalizer.js`: прежний мастер точек применяется транзакционно к подтверждённым source components; новые мероприятия остаются `review`.
- Provenance: `component.engineeringDecision`, `engineeringDecisionHistory`, `point.engineeringSources.physical`.
- Изменение ТМЦ после повторного импорта отмечается в QA, а старые решения не передаются автоматически иному физическому узлу.
- Очередь кандидатов не равна числу будущих точек, физические опоры без проверки не создавать.
- Edge `file://` и recovery на новой пользовательской базе — ручная приёмка, после неё можно закрывать Issue #12.
