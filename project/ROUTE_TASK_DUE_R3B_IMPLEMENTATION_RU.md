# LUBRICA — R3B: индивидуальные сроки и конкретные задания

**25.11.2026.** Продолжение R1/R2/R3A в [Draft PR #23](https://github.com/shonentez-afk/LUBRICA/pull/23). Main и production JSON не изменялись.

## Согласованная архитектура
Участок (с lineId для однозначной привязки) + вид обслуживания (категория реальной точки и операция) + одна периодичность. Тип машины не участвует в группировке. Постоянный маршрут является упорядоченным перечнем утверждённых taskId, а календарное задание — подмножеством мероприятий с конкретными сроками. Старые маршруты продолжают работать по старой логике.

## Реализованный сквозной цикл
1. R3A формирует проверенные черновики, не создаёт фиктивные точки и не меняет чужие маршруты.
2. Кнопка «Сроки мероприятий» открывает настройки каждого taskId. Для календаря — дата следующего обслуживания (можно заполнить одинаковую дату в пустых строках). Для моточасов — накопительное показание, дата показания, следующий накопительный порог и необязательная прогнозная наработка ч/сут. Не подставлять данные автоматически.
3. Активация типизированного автомаршрута разрешена после настройки всех индивидуальных сроков и инженерного QA. Проверка выполняется также при планировании и старте, не только в UI.
4. Планировщик формирует только ближайшее незакрытое обязательство каждого мероприятия. Группирует по дате в пределах маршрута, сохраняет исходный срок просроченных работ и порядок taskId. У уже запланированных/выполняемых мероприятий новые задания не создаются. Будущий долгосрочный прогноз моточасов не считается фактом; повторные обязательства не фиксируются до завершения текущего.
5. При фиксации плана сохраняются точные taskIds, dueEntries, ревизия постоянного маршрута и checklistSnapshot конкретного задания. Расчётная длительность: подготовка + число мероприятий задания × норма времени.
6. Из календаря открывается именно задание. Подготовка рассчитывает материал и инструмент по его taskIds. Изменение нормы/материала/параметров снимка или основания срока после фиксации блокирует запуск; снимок не переписывается. Нужно снять незапущенное задание и сформировать повторно. Редактор защищает состав маршрута с открытым заданием.
7. Запуск типизированного маршрута только из соответствующего незапущенного плана. Для календаря не раньше плановой и индивидуальной даты. Для моточасов требуется подтверждённое показание на фактическую дату, достигшее порога. Прогноз сам не разрешает выполнение.
8. В компактном и подробном чек-листе фактические моточасы на момент обслуживания обязательны для завершённого часового мероприятия. Следующий порог = факт + утверждённый интервал. Следующая календарная дата = дата выполнения + утверждённый интервал, с корректной календарной арифметикой. Дата задания фиксируется на запуске. Пропуск, «не требуется», отмена не продлевают срок; пропуск требует причины. Выполненный чек-лист и фактические показания остаются в истории. План/факт использует снимок задания, а не полный маршрут.

## Модель и модули
- `routes/route-due.js`: независимая модель `task.routeDue` с fingerprint физической точки/операции/интервала; nextDate или nextHours/readingHours/readingDate/hoursPerDay, lastRunId/lastServiceDate. Проверки, read-only preview, transactional configure, subset selection, frozen snapshot, completion/advance.
- `routes/route-engine.js`: активация, инженерные проверки, защита состава и параметров, поддержка R3A.
- `routes/route-planning.js`: task_due, одно ближайшее обязательство на taskId, резерв, точный subset, транзакционная фиксация снимка. UTC-календарная арифметика без timezone-сдвига; старые режимы сохранены.
- `routes/routes-ui.js`, `routes/route-planning-ui.js`, `routes/route-compact-ui.js`, `assets/route-compact.css`: настройки сроков, заполнение, открытие задания, подготовка, обязательное поле фактических моточасов в обоих режимах, печать старого формата.
- `checklist/checklist-engine.js`: точный снимок плана, проверка факта, обновление только выполненных задач и согласованная запись план/факт.
- `index.html`: локальная загрузка без сервера.
- `test/test_route_due_r3b.js`: сквозной Node-тест; `test/test_route_due_r3b_browser.py`: Chromium 1440/768; полный `bash test/run_all.sh`; отдельный ZIP R3B.
 
## Принятые ограничения и оставшиеся решения
- Исторические сроки не придумываются и не мигрируются автоматически. Пользователь задаёт начальные основания явно. Работа со счётчиком пока ручная, нет подключения к АСУ ТП, автоматического опроса, переноса накопления при сбросе/замене счётчика. Сброс требует отдельного инженерного согласования.
- Задание рассчитано на одну фактическую дату/смену; дата факта фиксируется на запуске. Долгосрочный календарь для новых маршрутов формирует ближайшие подтверждённые/прогнозные обязательства, а не цепочку будущих повторов без факта. Возможность многопериодного прогноза (отдельно, не как обязательные задания) — дальнейшее развитие.
- Если время и маршрут уже зафиксированы в открытом плане, изменение состава не выполняется автоматически. Требуется завершить/снять задания. После принятия R3B можно отдельно усовершенствовать обновление активных групп с согласованием ревизий.
- Автоматическая проверка использует синтетическую БД, не производственную. До ручной Edge file:// проверки на резервной копии и завершения K3/M1 не запускать реальную производственную эксплуатацию маршрутов. PR остаётся Draft, main не объединять.
