# LUBRICA — карта архитектуры

## 1. Сквозной поток данных

```text
Исходная производственная база / ручное добавление
            ↓
импорт → нормализация → классификация
            ↓
структура оборудования + компоненты
            ↓
физические точки обслуживания
            ↓
мероприятия точки
            ↓
анализ материала + инженерный расчёт + источник
            ↓
утверждённое мероприятие
            ↓
план смазки → маршрут → выполнение
            ↓
факт / ФРВ / аналитика / контроль
            ↓
Excel и производственная отчётность
```

## 2. Главные доменные различия

### Физическая точка ≠ мероприятие
Одна физическая точка может иметь несколько мероприятий. Нельзя сливать их в одну запись только ради упрощения UI.

### Маршрут ≠ генератор работ
Маршрут использует существующие утверждённые мероприятия. Он не создаёт новые мероприятия.

### Расчёт ≠ утверждение
Расчёт создаёт инженерный результат. Только после явного применения результат становится рабочим значением мероприятия.

### Архив ≠ удаление
Исторические и завершённые сущности должны сохранять жизненный цикл и не исчезать так, чтобы ломать фактическую историю.

## 3. Ключевые подсистемы

- `core/` — схема БД, нормализация, миграции, storage, safety, session;
- `import/` — импорт и классификация;
- `structure/` — дерево и физическая структура;
- `components/` — библиотеки, matching и binding;
- `bearings/` — библиотека и специализированная подшипниковая логика;
- `calculations/` — общий расчётный framework и адаптеры;
- `materials/` — материалы и инструменты;
- `lubrication/` — мероприятия физической точки;
- `machines/` — machine-specific profiles/constructors;
- `routes/` — маршруты, планирование, план/факт, аналитика;
- `checklist/` — выполнение и ФРВ;
- `qa/` — read-only контроль готовности;
- `export/` — финальный Excel;
- `ui/` — общие пользовательские экраны.

## 4. Инженерный слой

Расчётная архитектура должна разделять:
- исходные данные;
- распознанный тип узла;
- OEM-контекст;
- локальную доказательную таблицу;
- инженерный fallback;
- расчётный результат;
- применённый результат;
- источник и обоснование.

Machine profile может уточнять component-level OEM данные, если источник относится к конкретной машине.

## 5. Machine profiles и конструкторы

Конструктор машины должен:
- создавать только подтверждённые физические элементы;
- использовать устойчивые origin keys;
- быть идемпотентным;
- поддерживать imported и manually-added equipment;
- не скрывать неопределённость;
- не придумывать отсутствующие узлы;
- сохранять возможность расширения для новых машин.

## 6. Историческая устойчивость

Позднее изменение текущего маршрута, расчёта или справочника не должно переписывать уже завершённый факт. Для этого используются snapshot/revision и persisted provenance.

## 7. Экспорт

Критический контракт Excel:
**одна строка карты смазки = одно мероприятие (task)**.

Если одна физическая точка имеет несколько мероприятий, в Excel должны быть несколько строк с одним point и разными taskId.
