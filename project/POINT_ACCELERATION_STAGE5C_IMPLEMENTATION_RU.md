# LUBRICA Stage 5C.0 — ускоренное заполнение физических точек без замены конструкторов

**Дата:** 17.11.2026. **Рабочая ветка:** `feature/stage5b-conveyor-families-20261105`, PR #22 (draft). **Режим:** тестовая интеграционная реализация; базу предприятия и `main` не изменять. Данный Stage 5C.0 — инструменты до завершения всех конструкторов, а не начало маршрутной стадии.

## 1. Зафиксированное архитектурное решение

Вместо второго генератора физической карты введён дополнительный **слой над существующими** `LubricaClassifier`, `LubricaCandidateFinalizer`, `LubricaConveyorArrangement`, `LubricaEngineeringDecisions`, `LubricaAnalogs`, `LubricaTaskReadiness` и `LubricaProgramQA`. Он показывает инженерную очередь и готовит входные данные, но **не** создаёт точки без исходного ТМЦ, конкретного места, способа обслуживания, фактического источника и отдельного явного действия.

Не переписывать расчётные/OEM-движки, не изменять структуру вкладок карточки и архитектуру меню/дерева. Не создавать виртуальные опоры. Не переносить approval, taskId/pointId, факты, маршруты, монтажные положения и рассчитанные значения только потому, что название агрегата или подшипника совпало.

## 3. Что делать, если на валу конвейера нет данных о подшипнике

Варианты **строго различать**:

1. **Подшипниковый ТМЦ отсутствует, число неизвестно.** Статус `BEARING_SOURCE_UNKNOWN`. Уточнить по осмотру, OEM, фото, чертежу. Не создавать валовые опоры и `regrease` из двух валов.
2. **Модель ТМЦ указана, число неизвестно.** Статус `MODEL_KNOWN_COUNT_UNKNOWN`. Одна строка `UCP210` не доказывает 1, 2 или 4 опоры; это может быть обозначение типа для нескольких физических узлов.
3. **Число заявлено, но мест нет / осмотр не подтверждён.** `COUNT_REVIEW`. Это **не** входной параметр автоматического генератора; сохранить как запрос полевой проверки.
4. **Число и все реальные позиции подтверждены.** Инженер указывает каждое место отдельной записью; для каждой обслуживаемой опоры — точный source `componentId`, реальный доступ к маслёнке/каналу, тип обслуживания и ссылку на документ/фото. Только такие обслуживаемые позиции становятся **неотмеченными** кандидатами в штатном мастере.
5. **Позиция реальна, но модель пока неизвестна.** `SOURCE_REQUIRED`; место можно зафиксировать в реестре, но создавать точку с выдуманной маркой нельзя.
6. **Подшипник герметичный/не предназначен для внешней досмазки.** `not_serviceable` или `review` по OEM, без `regrease` по умолчанию. Не путать с ситуацией, где недоступна сама опора.
7. **Один ТМЦ в ведомости соответствует нескольким установленным опорам.** Допустимо назначить **один sourceComponentId** нескольким **разным, проверенным физическим местам**, каждое с собственным стабильным `conveyor_survey_<positionId>` в `candidateOriginKey`. Каждое физическое место — отдельный point; несколько операций на point — отдельные tasks в review.
8. **На машине уже есть точка на таком месте.** Новый survey не может создать вторую с той же позицией; менять ранее созданную survey-схему без отдельной сверки запрещено.

Для конвейеров, где двухвальная схема подтверждена, старые четыре места остаются **гипотетическими UI-слотами**, а не четырьмя подшипниками. Для роликовых, ламельных, шнековых, поворотных, цепных и гибридных конвейеров **четырёхопорный шаблон не переносить**. Системы охлаждения и все центрифуги/их дочерние подсистемы — `OUT_OF_SCOPE`, записи не изменяются.

## 4. Пробелы конструкторов — аудит фактического парка

Основание: `project/EQUIPMENT_CONSTRUCTOR_GAP_AUDIT_20261105_RU.md` из PR #21 (от 05.11), актуальный `project/FINAL_LUBRICATION_MAP_AND_ROUTES_MASTER_PLAN_RU.md`, существующий код Stage5B.12. **Числа физических точек по этим семействам неизвестны без осмотра и OEM**.

| Приоритет | Семейство | Действующая основа | Какой составной конструктор не закрыт |
|---|---|---|---|
| P0 | Конвейеры (226 похожих на машины; 293 записей с группами) | `Conveyor` + `Rotating` + element OEM | Код подтипов готов; нужны подтверждённые физические схемы всех вариантов, в том числе кратность одинаковых подшипников; survey добавлен |
| P0 | Пилы, поперечная/продольная резка, каретки, гильотины | `Rotating` + `linear_bearing` | `Saw / Cut & Traverse` — режущий вал, привод, каретка, линейные узлы и реальное обслуживание |
| P1 | Вентиляторы Ferrari/Ventapp-Tröster/REITZ/SNL/ZLG | `Fan Bearing Arrangement` | Дополнить неподтверждённые заводские схемы, не новые виртуальные DE/NDE |
| P1 | Питатели, дозаторы | `Rotating` + `chain` + gearbox | `Feeder Arrangement` (привод/фактические опоры/контуры) |
| P1 | Щёточная очистка и очистка ламелей | `Rotating` + `bearing` | `Brush / Cleaning` с фактической конструкцией щёток и привода |
| P1 | Штабеллеры, подъёмники, толкатели, упаковка | `Rotating`, `Oscillating`, screw/linear | `Handling / Stacker` (составная машина, защита от двойного учёта) |
| P1 | LINDNER VEGA 1500, прочие измельчители | component bearing/gearbox | `Shredder Rotor` только после OEM и подтверждения реальных опор |
| P2 | Масло-/гидростанции, насосные системы | общий `oil_system`, pump template | `Oil System Arrangement` с проверенными полостями и реальными точками контроля |
| P2 | Составные мотор-редукторы и мотор-барабаны | Motor/gearbox engines | `Drive Unit Arrangement` (раздельные реальныe полости, монтаж M1–M6) |

**Вне текущего объёма:** центрифуги, их масляный туман и системы охлаждения. Имена `other` не означают отсутствие 812 отдельных конструкторов. Машины без собственной смазки остаются контекстом с источником.

## 5. Тесты и дальнейшая приёмка

`test/test_stage5c_point_acceleration.js`: репрезентативные Node VM сценарии по двум линиям, повторяющейся модели подшипника при разных реальных местах, нулевому автоматическому числу точек, строгому источнику, сохранению approved/route/fact, безопасному пакетному решению, Excel preview и guarded bulk.

`test/test_stage5c_browser_ux.py`: Chromium browser реальных JS/CSS на синтетической базе, три размера 1440 / 768 / 390 px, инженерная очередь, открытие survey, две позиции одной модели, подтверждение, 0 автоматических точек, поиск и CSV. **390 px тестирует изолированную вкладку «Контроль»**, не всю десктопную оболочку/Android.

В PR требуется полный исторический regression и Stage5B tests. При невозможности автоматического UI/UX запуска — считать непринятым, не менять `main`. После CI и до слияния — ручная Edge `file://` приёмка **на копии** производственной JSON от 05.11.2026, сохранение 501 точек/517 мероприятий и ссылок на 45 approved/route/facts, повторное применение survey / Excel и физическая сверка всех применимых конвейеров. Персональные данные заводской базы не загружать в GitHub.

**Дальнейший порядок неизменен:** все конструкторы → полная карта точек/операций/OEM → реальные маршруты.
