## Архитектура и порядок реализации
1. Один контракт переходов и уникальности: статус маршрута draft/active/archived отделён от производственной готовности. Архив/восстановление/активация/удаление через одинаковые guards. Состав и открытые задания защищены; новые неготовые точки не сбрасывают активный маршрут. Не поддерживать параллельный legacy-автодвижок ради отсутствующих production routes.
2. Общая проверка task-level и job-level: QA, физическая точка, группа, источник срока, принадлежность/резерв, ППР, окно, норматив времени; конкретное задание использует точный набор taskId. Ошибки маршрута и ошибки отдельного задания не смешивать.
3. Единый расчёт срока, общих счётчиков, ППР и раннего окна. Технический scheduleKey неизменяем; общие подтверждённые настройки, индивидуальные пороги, отсутствие выдуманного факта. Недельные циклы предпочтительны, некратные интервалы не округлять вверх. ППР каждые 14 дней отдельно на линию. Дневной/сменный график и число смазчиков настраиваются независимо.
4. Календарь/подготовка/план/ресурс/запуск: проекция только для чтения; запись ближайших обязательств только подтверждённой транзакцией, снимок точного состава; готовые группы не блокируются другими; одна причина недоступности, видимая в интерфейсе.
5. Единое завершение: planned/in_progress/completed/partial/cancelled (точное внутреннее имя выбрать после проверки потребителей статуса); фиксировать результат каждого taskId, сохранять историю, продвигать только реально выполненные сроки; незавершённое снова доступно планированию. Отчёты, экспорт, архив, аналитика и счётчики используют один итог выполнения.
6. Сквозная проверка всех потребителей, сохранения/reload, повторного создания и stale preview. Тесты должны выявлять дефекты исходного HEAD до изменения, а после проходить. Не ослаблять QA, OEM, расчёты и существующие регрессии для достижения PASS.
